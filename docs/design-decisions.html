Backend · Security

1. JWT Authentication

🔑 Why JWT (JSON Web Tokens)? JwtUtil.java · JwtAuthFilter.java · AuthController.java

The system serves three distinct user roles — Candidate, Employer, and Admin — from a single API. After login, every subsequent request must carry proof of who the user is and what role they hold. JWT solves this without the server needing to remember anything.

✅ Why JWT
  • Stateless — the server holds no session table. Any node can validate a request independently.
  • Self-contained — the token carries email, role, and userId as claims; no DB lookup needed to know who is calling.
  • Role enforcement is trivial — Spring Security reads the role claim and maps it to ROLE_CANDIDATE / ROLE_EMPLOYER automatically.
  • Works with CORS — the React dev server on port 5173 and the Spring server on 8080 share only the cookie; no CSRF issue because SameSite semantics apply.
❌ Why not Session-based auth
  • Sessions require server-side storage (memory / Redis). Adds infrastructure.
  • Horizontal scaling becomes harder — session affinity or a shared store is needed.
  • Not REST-idiomatic; HttpSession is an artifact of server-rendered web apps.
  • Spring Security's SessionCreationPolicy.STATELESS is set explicitly to avoid accidental session creation.

How it is implemented

Token generation — JwtUtil.java
Jwts.builder()
  .subject(email)         // used as @AuthenticationPrincipal in controllers
  .claim("role", role)    // CANDIDATE | EMPLOYER | ADMIN
  .claim("userId", userId)
  .expiration(new Date(now + expirationMs))   // 24 h default
  .signWith(Keys.hmacShaKeyFor(secret.getBytes(UTF_8)))
  .compact()

HMAC-SHA256 signing with a secret injected from app.jwt.secret (environment variable in production).

Token validation — JwtAuthFilter.java (runs on every request)
Read cookie "jwt"
→
Fallback: Authorization header
→
isTokenValid?
→
Set SecurityContext

The filter extends OncePerRequestFilter so it runs exactly once per request. If the token is absent or invalid, the security context is simply left empty; Spring Security's later rules reject the request with 401 or 403.

Where the JWT lives — dual-channel token delivery

✅ Primary: HttpOnly Cookie

Set by AuthController.setJwtCookie() on login/register. Browser attaches it automatically to every withCredentials: true request. JavaScript cannot read it, so XSS cannot steal it.

↩ Fallback: Bearer header

Filter also checks Authorization: Bearer <token>. Used by curl tests, Postman, and the Swagger UI (which cannot set cookies). Not the production path.

Backend · Security

2. Password Hashing with BCrypt

🔒 Why BCrypt over MD5 / SHA / plain text? SecurityConfig.java · AuthService.java
✅ Why BCrypt
  • Slow by design — the work factor (cost) makes brute-force attacks computationally expensive. MD5/SHA are fast, which is bad for password storage.
  • Built-in salt — each hash is unique even for identical passwords. No rainbow table attack is possible.
  • Spring-native — BCryptPasswordEncoder is the recommended PasswordEncoder and is wired as a @Bean in SecurityConfig.
❌ Why not SHA-256 / MD5
  • They are general-purpose hash functions — fast to compute, so billions of guesses per second are possible with GPUs.
  • Without salting, identical passwords produce identical hashes, enabling pre-computed table attacks.
  • MD5 is broken for cryptographic purposes.
Usage pattern
// Registration — hash and store
candidate.setPasswordHash(passwordEncoder.encode(req.getPassword()));

// Login — compare plaintext to stored hash
if (!passwordEncoder.matches(req.getPassword(), candidate.getPasswordHash())) {
    throw new IllegalArgumentException("Invalid credentials");
}

The raw password never touches the database. The field is named passwordHash in every entity to make the intent explicit.

Backend · Security

3. HttpOnly Cookie Strategy

🍪 Why store JWT in a cookie instead of localStorage? AuthController.java · frontend/api/axios.js
✅ Why HttpOnly Cookie
  • XSS-safe — HttpOnly means no JavaScript (including injected scripts) can call document.cookie to steal the token.
  • Automatic attachment — with withCredentials: true in Axios, the browser sends the cookie with every request without any manual header management in React code.
  • Logout is clean — overwriting the cookie with MaxAge=0 in the logout endpoint instantly invalidates it on the client.
❌ Why not localStorage
  • localStorage is readable by any JavaScript on the page. A single XSS vulnerability exposes the token.
  • Many security guidelines (OWASP) explicitly warn against storing JWTs in localStorage for sensitive applications.
  • Requires manual Authorization header injection in every API call.
What IS stored in localStorage (non-sensitive UI state only)
localStorage.setItem('role', data.role)       // CANDIDATE / EMPLOYER / ADMIN
localStorage.setItem('userId', data.userId)   // for display only
localStorage.setItem('name', data.name)       // greeting in nav bar

The actual JWT is in the cookie. localStorage only holds metadata needed to show the right dashboard UI without an extra API call.

Backend · Code Style

4. No Lombok — Explicit Getters & Setters

📝 Why write 50 lines of getters/setters instead of @Data? All entity/*.java · dto/*.java

Lombok is in the pom.xml (optional scope) but deliberately unused in the entity and DTO code. The choice is intentional.

✅ Why explicit getters/setters
  • Transparent to any IDE — no annotation processor needed. Compile, navigate, debug, refactor without plugin dependencies.
  • Academic requirement — the assignment specification explicitly forbids Lombok to demonstrate understanding of Java encapsulation.
  • Debuggability — you can set a breakpoint inside a setter to trace when a field changes. With @Data that code is generated and invisible.
  • No surprises with Hibernate — Lombok's @EqualsAndHashCode on JPA entities causes well-known proxy issues. Explicit methods avoid this entirely.
❌ Why @Data / @Getter / @Setter would work too
  • Reduces boilerplate by ~70% for large entity classes.
  • Industry standard in production Spring apps — well-understood by most Java developers.
  • Not used here because the assignment asked for demonstrating language fundamentals.
Pattern used consistently
private String designation;

public String getDesignation() { return designation; }
public void setDesignation(String designation) { this.designation = designation; }

All 8 entities and all DTOs follow this pattern. Single-line body form keeps the class readable.

Backend · Code Style

5. Constructor Injection — No @Autowired Fields

🏗️ Why constructor injection instead of @Autowired on fields? Every service and controller class
✅ Why constructor injection
  • Immutability — dependencies are final and set once. No null-state between construction and injection.
  • Testability — unit tests can pass mock objects directly in the constructor without a Spring context.
  • Explicit dependencies — looking at the constructor immediately shows what the class needs.
  • Spring best practice since 4.3 — with a single constructor, @Autowired is not even needed.
❌ Why not @Autowired field injection
  • Fields are injected via reflection, bypassing Java's visibility rules.
  • Class can be constructed in a "broken" state if the Spring container is bypassed.
  • IntelliJ, SonarLint, and Spring's own documentation flag it as a code smell.
  • Makes circular dependencies harder to detect at startup.
Pattern in every service
@Service
public class ApplicationService {
    private final ApplicationRepository applicationRepository;
    private final CandidateRepository candidateRepository;
    // ...

    public ApplicationService(ApplicationRepository applicationRepository,
                               CandidateRepository candidateRepository, ...) {
        this.applicationRepository = applicationRepository;
        this.candidateRepository   = candidateRepository;
        // ...
    }
}
Backend · Database

6. String Fields for DB-enum Columns (application status, interview mode)

🗄️ Why plain String instead of a Java enum for status columns? Application.java · Interview.java

The MySQL schema defines status on applications as ENUM('Applied','Interview Scheduled','Interview Completed',...). These values contain spaces and hyphens. This creates a critical problem with Java enums.

✅ Why plain String + @Column(columnDefinition="ENUM(...)")
  • Exact match — Java stores and reads "Interview Scheduled" exactly as it appears in the MySQL enum definition.
  • ddl-auto=validate passes — Hibernate compares the column definition at startup. A mismatch throws an error and prevents the app from starting.
  • No mapping code — no @Converter or toString() override needed.
❌ Why not @Enumerated(EnumType.STRING)
  • Java enum names cannot contain spaces. INTERVIEW_SCHEDULED does not equal "Interview Scheduled".
  • Hibernate would throw a mapping validation error at startup because the stored string doesn't match any enum name().
  • A @Converter would solve it but adds complexity — plain String is simpler and equally readable.
DB schema (actual MySQL)
status ENUM('Applied','Shortlisted','Interview Scheduled','Interview Completed',
            'Selected','Offered','Recruited','Rejected','Withdrawn') DEFAULT 'Applied'

mode   ENUM('In-Person','Online','Telephonic') DEFAULT 'In-Person'
Entity mapping
@Column(columnDefinition = "ENUM('Applied','Shortlisted',...)")
private String status = "Applied";

The columnDefinition attribute tells Hibernate what to expect during schema validation, not what to create (since ddl-auto=validate never creates tables).

Backend · Error Handling

7. Exception-to-HTTP-Status Mapping

⚠️ Why throw exceptions instead of returning error ResponseEntities from services? GlobalExceptionHandler.java · all service classes
✅ Why throw exceptions in services
  • Separation of concerns — services don't know about HTTP. They throw business exceptions; the handler layer translates to status codes.
  • Clean service signatures — methods return domain objects, not ResponseEntity<?>. Easy to test and reuse.
  • @RestControllerAdvice centralizes all error responses — one place to change the error body format.
❌ Why not return ResponseEntity from service
  • Services become HTTP-aware, breaking the layered architecture.
  • Callers must unwrap the entity; calling a service from a scheduler or test becomes awkward.
Exception-to-status mapping table

Note: "Already applied" throws IllegalArgumentException → 400. The spec mentioned 409 Conflict; 400 was used because the existing handler doesn't have a 409 mapping and adding one was out of scope.

Backend · Persistence

8. Spring Data JPA + Hibernate — ddl-auto=validate

🗃️ Why JPA/ORM instead of plain JDBC? And why validate, not create? application.properties · all repository interfaces
✅ Why Spring Data JPA
  • Zero boilerplate repositories — JpaRepository provides save, findById, deleteById etc. with no SQL. Derived query methods (findByCandidate_CandidateId) are generated from the method name.
  • Object graph navigation — lazy-loaded @ManyToOne associations let the service traverse app.getVacancy().getEmployer().getEmail() naturally.
  • Transaction management — @Transactional on service methods ensures atomic multi-step operations (apply + notify, schedule interview + update application status).
❌ Why not plain JDBC / JdbcTemplate
  • Requires hand-writing every SELECT, INSERT, UPDATE, DELETE.
  • Object mapping (ResultSet → Java object) must be done manually.
  • Fine for simple queries but becomes verbose for complex associations.
Why ddl-auto=validate (not create / update)?

The 9 tables were designed and created manually in MySQL before development began. validate means Hibernate compares the entity field definitions against the actual DB schema at startup and throws an error if they don't match — it never alters the database. This prevents accidental schema drift and forces entity classes to exactly mirror the agreed-upon schema.

Lazy vs Eager loading choice
@ManyToOne(fetch = FetchType.LAZY)   // used for all associations
@JoinColumn(name = "vacancy_id")
private Vacancy vacancy;

LAZY means the associated Vacancy is not fetched until getVacancy() is called. This avoids N+1 query issues and cartesian product joins when only a list of application IDs is needed. The service methods navigate associations explicitly when they need them.

Backend · Notifications

9. Dual-channel Notification System (DB + Email)

🔔 Why save notifications to the DB AND attempt email, with silent email failure? NotificationService.java · Notification.java · NotificationController.java
✅ DB-first notification strategy
  • In-app notification bell — the frontend's notification page polls GET /api/notifications. This requires DB persistence regardless of email.
  • Email failure is non-critical — SMTP may be unconfigured in dev. Wrapping email in try/catch and logging a warning means the main business operation (apply, schedule interview) always succeeds.
  • Audit trail — the notifications table records every status change event. Useful for disputes and debugging.
❌ Why not email-only
  • SMTP not always configured — would break the whole apply flow during development.
  • No in-app notification history.
  • No offline support — if the user's email server is down, the notification is permanently lost.
Flow
Service triggers notify()
→
Save to notifications table
→
Attempt SMTP email
→
Log warn if fails, continue

SMTP is skipped automatically if spring.mail.username contains the placeholder "your-email", avoiding connection timeouts in dev.

Why @Autowired(required=false) for JavaMailSender
@Autowired(required = false)
private JavaMailSender mailSender;

If SMTP credentials are not configured, Spring cannot create the JavaMailSender bean. required=false means mailSender will be null and the null check in sendEmail() skips it cleanly instead of crashing the app on startup.

Backend · AI Feature

10. AI Resume Analysis via SAP Hyperspace LLM

✨ Why use an LLM for resume scoring? Why not keyword matching? AiAnalysisService.java · ResumeController.java · application.properties
✅ Why LLM-based analysis
  • Semantic understanding — a candidate who listed "React.js" matches a job requiring "frontend development" even without the exact keyword.
  • Structured output — the prompt demands {"score": 0-100, "summary": "..."}. The score is stored in ai_score and surfaces as a sortable badge in the UI.
  • SAP Hyperspace — uses the internal SAP AI proxy at localhost:6655/openai/v1, which is already running in the dev environment (the same proxy used by Claude Code). No external API key or cost.
❌ Why not keyword matching
  • Brittle — misses synonyms, abbreviations, context.
  • Requires maintaining a skills taxonomy.
  • Scores are arbitrary counts, not a holistic fit assessment.
Why Apache PDFBox for text extraction?

Resumes are uploaded as PDFs. PDFBox (Apache, open-source) extracts the plain text. The text is truncated to 4,000 characters before sending to the LLM to stay within token limits. PDFBox is a pure Java library — no native dependencies or external services.

Why Java HttpClient instead of a Spring/OkHttp client?

Java 11's built-in java.net.http.HttpClient is used for the LLM API call. No new dependency needed — the OpenAI-compatible API is called with a simple POST with a JSON body. Adding a dedicated HTTP client library would be over-engineering for a single API call.

Backend · Automation

11. @Scheduled Vacancy Expiry Job

⏰ Why a scheduled job instead of checking deadline at query time? VacancyExpiryScheduler.java
✅ Why proactive DB update at midnight
  • Consistent state — after the cron runs, the status column is authoritative. No conditional logic scattered across every vacancy query.
  • Works with the public endpoint — GET /api/vacancies/open filters by status = 'Open'. If we didn't update the DB, we'd need deadline filtering in every query.
  • Simple cron expression — 0 0 0 * * * = midnight every day. Easy to change if requirements change.
❌ Why not filter at query time
  • Every vacancy list query would need WHERE deadline > NOW(). Easy to forget in one place.
  • Admin stats (openVacancies count) would also need the filter.
  • Stale "Open" records accumulate, making DB state misleading.
Backend · Developer Experience

12. OpenAPI / Swagger UI (springdoc)

📖 Why springdoc-openapi? OpenApiConfig.java · application.properties · all controllers (@Tag, @Operation)
✅ Why Swagger UI
  • Live interactive documentation — available at /swagger-ui.html. Any team member can test endpoints without Postman.
  • Auto-generated from code — no separate spec file to maintain. Annotations on controllers (@Tag, @Operation) enrich the docs.
  • springdoc 2.x for Spring Boot 3 — the older springfox library is incompatible with Spring Boot 3+. springdoc is the maintained replacement.
❌ Why not springfox
  • springfox has not been maintained since 2022 and is broken with Spring Boot 3 / Spring 6 (reflection changes).
  • Many open GitHub issues with no resolution.
Frontend · Tech Stack

13. React 18 + Vite for the Frontend

⚛️ Why React? Why Vite over CRA? frontend/src/App.jsx · frontend/vite.config.js
✅ Why React
  • Component model — every page (e.g. ApplicationsPage, InterviewsPage) is a self-contained component with its own state and UI. Easy to develop independently.
  • Hooks — useState and useEffect handle data fetching and UI state without class boilerplate.
  • Ecosystem — React Router for navigation, React Icons for icon sets, Axios for HTTP.
Why Vite over Create-React-App (CRA)
  • Vite uses native ES modules in dev — cold start is near-instant (<1s vs 15–30s for CRA on large projects).
  • CRA is officially deprecated by the React team.
  • Vite's proxy config (server.proxy) forwards /api to Spring on port 8080 so CORS is never needed during development.
Frontend · Navigation

14. React Router v6 — Client-side Routing

🗺️ Why client-side routing? How does ProtectedRoute work? App.jsx · ProtectedRoute.jsx
✅ Why client-side routing
  • SPA architecture — once the JS bundle loads, navigation between pages is instant (no full page reload). The candidate dashboard, job search, and applications pages all share one app shell.
  • Programmatic navigation — after login, navigate('/candidate/dashboard') sends the user to the right page based on their role.
How ProtectedRoute guards work

The ProtectedRoute component checks localStorage.getItem('role'). If absent, redirects to /login. If role doesn't match (e.g. a candidate trying to visit /employer/dashboard), redirects accordingly. The actual security is enforced by the JWT on the server — the client guard is only UX.

Route structure
/                     → LandingPage (public)
/login                → Candidate login
/employer/login       → Employer login
/register             → Candidate registration
/candidate/dashboard  → ProtectedRoute(CANDIDATE) → CandidateDashboard
/employer/dashboard   → ProtectedRoute(EMPLOYER)  → EmployerDashboard
/admin/dashboard      → ProtectedRoute(ADMIN)     → AdminDashboard
Frontend · HTTP

15. Axios Instance with Interceptors

🌐 Why a shared axios instance instead of fetch()? frontend/src/api/axios.js
✅ Why axios + shared instance
  • baseURL — all API calls use /api as base. No URL duplication across 15+ pages.
  • withCredentials: true — set once; every request automatically sends the HttpOnly JWT cookie. No manual header code anywhere.
  • Response interceptor — 401 responses automatically clear localStorage and redirect to /login. Session expiry is handled globally.
❌ Why not native fetch()
  • fetch() requires manual JSON serialization and .json() parsing every time.
  • No built-in interceptors — the 401 redirect logic would need to be duplicated in every API call.
  • Error handling is awkward — fetch only rejects on network errors, not 4xx/5xx.
The interceptor
api.interceptors.response.use(
  res => res,
  err => {
    if (err.response?.status === 401) {
      localStorage.clear()
      window.location.href = '/login'
    }
    return Promise.reject(err)
  }
)

If the JWT expires (after 24h) and the user tries any authenticated action, they are silently redirected to login without seeing a confusing error message.

Frontend · Architecture

16. Local Component State (useState) — No Redux / Zustand

🧠 Why no global state manager? All page components
✅ Why local useState per page
  • Pages are independent — the Applications page data has nothing to share with the Vacancies page. No cross-page state.
  • Simpler mental model — each page fetches its own data on mount (useEffect), displays it, and updates it on user action. No store, no actions, no reducers.
  • Academic scope — Redux/Zustand add significant boilerplate. For 5 role-scoped pages, it is over-engineering.
❌ When you'd add Redux / Zustand
  • When the same data (e.g. user profile, notification count) needs to be shown in multiple unrelated components simultaneously.
  • When there is complex optimistic update logic that spans multiple pages.
  • Neither case applies here — the notification badge could be the one exception, but it is re-fetched per page instead.

Frontend · Styling

17. Bootstrap 5 for UI Components

🎨 Why Bootstrap? Why no Tailwind or Material UI? All JSX pages (className="btn btn-primary", "card", etc.)
✅ Why Bootstrap 5
  • Speed — pre-built classes for cards, forms, buttons, modals, grids. The UI was built in hours, not days.
  • No build step needed — Bootstrap is a pure CSS library. No CSS-in-JS, no PostCSS config, no Tailwind purge setup.
  • Familiar to the team — both team members have prior Bootstrap exposure; zero onboarding cost.
  • Inline style overrides — the dark theme (background: #0f172a) and custom elements (status badges, score chips) use inline styles for precision, layered on top of Bootstrap defaults.
Why not Tailwind / MUI / Chakra
  • Tailwind — requires a build pipeline with PostCSS and careful purge config. Utility classes become verbose in JSX. Good for large teams, overkill for a 2-person academic project.
  • Material UI / Chakra — opinionated design language that fights against customisation. Getting to a dark, professional recruiter-portal look requires significant theme overriding.
Custom styling approach

Bootstrap provides the grid (row / col), utilities (d-flex, gap-2, fw-semibold), and base components. Colour, border-radius, and shadow customisations are applied with inline style={{}} props on individual elements. This avoids a custom SCSS compilation step while keeping full visual control over the dark theme palette.

Backend + Frontend · Trust & Safety

18. Report System — Mutual Accountability

🚩 Why a report system? Why can both sides report each other? ReportService.java · Report.java · ReportController.java · ApplicationsPage.jsx
✅ Why bidirectional reporting
  • Employer reports candidate — fake credentials, no-show, unprofessional behaviour. Protects employers from bad actors.
  • Candidate reports employer — discriminatory behaviour, false job descriptions, harassment. Protects candidates.
  • Admin dashboard — reports surface in the admin panel per user with a count badge. Admin can deactivate accounts if needed.
Design decisions in reports
  • One report per pair — a unique constraint check (existsByReporterTypeAndReporterIdAndReportedTypeAndReportedId) prevents duplicate reporting.
  • Reason includes star rating + category + details — the frontend concatenates these into a structured string before submission, giving admins structured information even from a plain-text field.
