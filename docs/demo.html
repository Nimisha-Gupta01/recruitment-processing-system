Likely Questions from the Lecturer
Why Spring Boot and not Node.js or Django?
Spring Boot gives us strong typing, built-in dependency injection, JPA/Hibernate ORM, and production-grade security via Spring Security — all out of the box. For an enterprise recruitment system where data integrity matters, Java's type safety reduces runtime errors. Spring Security's filter chain (JwtAuthFilter) makes it easy to plug in custom authentication without reinventing the wheel.
Why MySQL and not MongoDB or PostgreSQL?
Recruitment data is highly relational — candidates, vacancies, applications, and interviews all reference each other with foreign keys. MySQL 8 gives us full ACID transactions, enum columns that prevent invalid status values at the DB level, and window functions for analytics. MongoDB would require manual join logic for every query that crosses entity boundaries.
Why JWT stored in httpOnly cookie instead of localStorage?
If the JWT were in localStorage, any XSS vulnerability (injected script on the page) could read and steal it. An httpOnly cookie cannot be accessed by JavaScript at all — only sent automatically by the browser on each request. The tradeoff is CSRF risk, which we mitigate with SameSite cookie policy. This is the recommended pattern for browser-based apps.
JWTAuthController.setJwtCookie() — cookie.setHttpOnly(true), cookie.setPath("/"), MaxAge = expirationMs / 1000
axioswithCredentials: true in axios.js ensures the cookie is sent with every cross-origin request to localhost:8080
What does the AI actually do — is it real?
Yes. AiAnalysisService.java sends the job description and the candidate's cover note to an AI API endpoint. The prompt asks it to score the candidate 1–100 and write a plain-English summary explaining the reasoning. The score and summary are stored on the applications table columns ai_score and ai_summary. This runs automatically on application submission — no manual trigger needed.
What prevents an employer from seeing another employer's applications? (IDOR)
Every service method checks ownership before returning data. In ApplicationService.getVacancyApplications(): if (!vacancy.getEmployer().getEmail().equals(employerEmail)) throw new SecurityException("Access denied"). Even if an attacker has a valid EMPLOYER JWT and guesses another employer's vacancyId, they get a 403. This is called IDOR prevention (Insecure Direct Object Reference).
ServiceApplicationService.java → getVacancyApplications()
vacancy.getEmployer().getEmail().equals(employerEmail) — throws SecurityException if false
What is the 3-month reapply cooldown?
After a candidate withdraws an application, they cannot re-apply to the same vacancy for 3 months. This prevents gaming the system (apply → withdraw → apply again repeatedly). In ApplicationService.apply(), if a prior withdrawn application exists, it computes withdrawnAt.plusMonths(3) and throws an IllegalArgumentException with the exact re-apply date if the cooldown hasn't passed.
ServiceApplicationService.java → apply()
Finds prior withdrawn record → withdrawnAt.plusMonths(3) → if now.isBefore(earliestReapply) → throws with message "You may apply again from YYYY-MM-DD"
Why is the Applications page a two-panel layout instead of a table?
Tables can only show a few columns before requiring horizontal scroll. A two-panel layout lets the employer see the full application detail — AI summary, cover note, resume, and all action buttons — without navigating away from the list. This is the same UX pattern used by Gmail, Outlook, and Jira. The left panel gives a quick scannable overview; the right panel gives depth on demand.
How does ddl-auto=validate work and why not auto-create?
ddl-auto=validate tells Hibernate to check that the entity classes match the existing database schema on startup — but never create or alter any tables. This is the production-safe setting. Schema changes are made manually via ALTER TABLE SQL scripts. If Hibernate detects a mismatch (e.g. a missing column), it throws an error at startup and prevents the app from running with inconsistent schema.
